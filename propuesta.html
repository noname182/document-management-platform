Propuesta Técnica Integral: Plataforma Documental & DevOps QA

Resumen de Arquitectura v2.0: Monorepo desacoplado en 2 microservicios especializados[cite: 11]. Servicio 1 (Core API en PHP Laravel 11) gestiona autenticación JWT, autorización híbrida (RBAC con 5 roles y motor de políticas ABAC), control de concurrencia pesimista (Check-out/Check-in), reversión segura (Forward-Rollback) y persistencia relacional en PostgreSQL 16[cite: 11]. Servicio 2 (Doc Processor en Node.js 20+) administra I/O masivo por streaming, análisis de magic bytes, cálculo criptográfico SHA-256 en memoria, cuarentena automática contra malware y almacenamiento S3 sobre un clúster MinIO particionado en 3 buckets globales[cite: 11]. Incorpora pruebas unitarias, de integración, de contrato (Microcks), seguridad estática/dinámica (SonarQube/OWASP ZAP), pruebas de rendimiento (k6) y pipeline CI/CD[cite: 11].

1. Arquitectura del Sistema: Desacoplamiento de Microservicios

  • Microservicio 1: Core API (PHP 8.3 / Laravel 11): Maneja peticiones HTTP ligeras de metadatos (10-25 ms), catálogo de categorías/departamentos, evaluación de reglas lógicas ABAC en JSONB, registro inmutable en auditoría forense (append-only) y emisión de candados transaccionales[cite: 11].
  • Microservicio 2: Doc Processor (Node.js 20+): Procesa transferencias multipart de archivos por flujo de bytes (streams) sin bloquear el hilo principal[cite: 11]. Inspecciona cabeceras binarias (magic bytes) para prevenir extensiones fraudulentas, ejecuta escaneo automático de firmas y calcula el hash SHA-256 definitivo directamente hacia MinIO[cite: 11].

2. Arquitectura de Almacenamiento S3 (MinIO) y Cuarentena Automática

El almacenamiento no crea depósitos físicos por empresa. Utiliza 3 buckets globales de infraestructura y aísla a los inquilinos mediante prefijos de clave lógica (Key prefixes) direccionados por el hash SHA-256 del binario:

Bucket Global Tipo de Objeto Estructura de Clave S3 (Key) Política y Ciclo de Vida
quarantine-vault Binarios recién subidos {tenant_slug}/temp_{upload_token}.bin Aislamiento automático. Auto-purga transcurridas 24 horas.
documents-vault PDF, DOCX, XLSX, TXT {tenant_slug}/docs/{document_id}/v{n}/{sha256}.{ext} Inmutable. Indexación de texto para búsqueda y versionado.
media-vault Video médico, DICOM, RAW {tenant_slug}/media/{document_id}/v{n}/{sha256}.{ext} Permite subida multipart por bloques y URLs prefirmadas.

Pipeline de Cuarentena 100% Automático: El archivo se recibe inicialmente en quarantine-vault. El microservicio en Node.js inspecciona los primeros 512 bytes (magic bytes) contrastándolos con el MIME declarado y ejecuta el escáner antivirus. Si el binario resulta infectado o alterado, se retiene con estado QUARANTINED y se notifica al log forense; si resulta íntegro, se promueve al bucket definitivo (documents-vault o media-vault), registrando la versión en PostgreSQL y eliminando el archivo temporal de cuarentena.

3. Modelo de Autorización Híbrido: RBAC + Motor ABAC Dinámico

El sistema combina una jerarquía de roles universales con evaluación condicional basada en atributos (ABAC):

Rol Permisos Atómicos (permission_key) Evaluación Contextual ABAC (access_policies)
VIEWER doc:read, doc:download Permite lectura exclusivamente si el documento tiene estado APPROVED y pertenece al tenant.
EDITOR doc:read, doc:download, doc:create, doc:checkout, doc:checkin, doc:discard_checkout, doc:rollback Acceso condicionado a que user.department_id == category.department_id. Rollback habilitado únicamente en borradores propios pendientes de aprobación.
APPROVER doc:read, doc:download, doc:approve, doc:reject, doc:rollback, audit:read Revisión y rollback transversal a nivel de organización para control de calidad y cumplimiento normativo.
TENANT_ADMIN Matriz completa de Approver + doc:force_unlock, user:manage, dept:manage Administración integral de la estructura organizativa y liberación forzada de bloqueos huérfanos.
SYSTEM_ADMIN Matriz global + quarantine:manage, system:metrics, tenant:manage Control de infraestructura del clúster MinIO, métricas del sistema y desbloqueo de falsos positivos.

4. Control de Concurrencia y Gobernanza Forense (Forward-Rollback)

  • Check-out / Check-in Transaccional: Al solicitar edición (doc:checkout), PostgreSQL activa un candado pesimista estableciendo is_locked = TRUE, locked_by_user_id = user_id y locked_at = CURRENT_TIMESTAMP. Peticiones concurrentes sobre el documento son denegadas inmediatamente con código HTTP 423 (Locked).
  • Reversión hacia Adelante (Forward-Rollback con clave doc:rollback): Para garantizar la cadena de custodia y la inmutabilidad documental, una versión errónea nunca se elimina física ni lógicamente. Al solicitar restaurar una versión anterior (ej. v1 sobre la errónea v2), el sistema genera la versión v3 apuntando al hash SHA-256 de la v1 original sin duplicar espacio en MinIO, marcando la v2 como DEPRECATED y registrando el evento en document_audit_logs.

C. Pruebas de Casos de Borde (Boundary / Edge Cases)

Comprueban el comportamiento del sistema en los límites permitidos, donde se concentran las fallas de seguridad y bugs[cite: 14]:

  • Valor mínimo permitido y valor inmediatamente inferior (ej. archivo de 0 bytes o token vacío)[cite: 14].
  • Valor máximo permitido e inmediatamente superior (ej. archivo de 5.01 GB intentando ingresar a media-vault)[cite: 14].
  • Valores atípicos: binarios ejecutables con extensión .pdf simulada, nombres con inyecciones de ruta (../../) y peticiones simultáneas de check-out en milisegundos idénticos[cite: 14].

7. Pruebas de Carga y Rendimiento con k6

Se evalúa la estabilidad del sistema mediante cuatro perfiles de tráfico en k6[cite: 15]:

  • 1. Load Testing (Carga esperada): Evalúa el rendimiento durante el volumen habitual de usuarios simultáneos navegando y consultando metadatos[cite: 15].
  • 2. Stress Testing (Límite): Incrementa la concurrencia progresivamente hasta hallar el punto de quiebre de conexiones en PostgreSQL y MinIO[cite: 15].
  • 3. Spike Testing (Pico violento): Simula ráfagas masivas de peticiones de check-out en segundos para verificar la consistencia de los candados sin caídas[cite: 15].
  • 4. Soak Testing (Resistencia prolongada): Mantiene una carga media durante varias horas continuas para detectar fugas de memoria en Node.js o saturación en disco[cite: 15].

8. Pruebas de Contrato con Microcks (OpenAPI 3.0)

Microcks actúa como servidor de simulación (mocking) y validador de contratos OpenAPI 3.0 en CI/CD[cite: 16]:

Característica Mock en Código (PHPUnit / Jest) Microcks (API Mocking)
¿Dónde vive? En el archivo de test local[cite: 16]. En un contenedor o servidor independiente[cite: 16].
¿Qué simula? Clases, métodos o llamadas internas en código[cite: 16]. Endpoints REST completos entre Laravel y Node.js[cite: 16].
Propósito Probar lógica aislada sin dependencias externas[cite: 16]. Permitir el avance desacoplado del frontend y verificar que los servicios no rompan el contrato API[cite: 16].

El Ciclo de Contratos en CI/CD: Si el Frontend y el Core API acuerdan en processor-contract.yaml que la respuesta de subida exige el atributo sha256_hash, pero el Doc Processor responde por error hash, Microcks frena el pipeline con error en rojo antes del despliegue: "Violación de contrato: se esperaba 'sha256_hash', pero se recibió 'hash'"[cite: 16].

9. Seguridad: SAST (SonarCloud) vs. DAST (OWASP ZAP)

Característica SAST (Estático - SonarCloud) DAST (Dinámico - OWASP ZAP)
¿App encendida? No. Lee archivos de código fuente en reposo[cite: 16]. Sí. Requiere que los contenedores estén encendidos y respondiendo[cite: 16].
Punto de vista Caja Blanca (White-box): conoce el código fuente[cite: 16]. Caja Negra (Black-box): actúa como atacante externo[cite: 16].
Qué detecta Inyecciones SQL, credenciales expuestas en plano, code smells[cite: 16]. Cabeceras HTTP sin flag seguro, fallos CORS, fugas de traza y XSS[cite: 16].
Momento Al compilar o en cada commit / Pull Request[cite: 16]. Al desplegar en entornos de prueba (Staging)[cite: 16].
